# daily-budget — project memory

## Product philosophy
Базовый прогноз дневного бюджета при **минимальном вводе**. Сознательно НЕ
дневной трекер трат: пользователь просто вводит фактический остаток, когда хочет
обновить данные — прогноз `(остаток − фикс − сбережения) / дни` самокорректируется
на всё потраченное по факту. Rollover недотрат/перетрат происходит естественно
(остаток ÷ оставшиеся дни). Полноценный трекер — возможно в будущем, отдельная
функциональность.

## Future ideas (планы)
1. **Настраиваемый желаемый положительный остаток** — ✅ **реализовано** (ветка
   `daily-limit-improvements`). Буфер вынесен из хардкода в синхронизируемый
   скаляр `buffer` (+`meta.buffer`), мёржится отдельно как `bank`/`incomeDay`;
   `coerceBuffer` сохраняет явный `0`. Редактируется в **Settings → Budget**
   (`SettingsTab/BufferCard`), питает `perDayGreen`/`computeSituation`. Тесты —
   `test/storage/buffer.test.ts`.
2. **Индикатор опережения в виджете** — ✅ **реализовано** (ветка
   `claude/remaining-features-zzi7ou`). Показывает, насколько пользователь идёт
   с опережением/отставанием от плана (делает «тихую» экономию видимой). Эталон
   плана — **плановый темп от опционального месячного дохода**, без снапшотов и
   якорей (stateless: опечатка в остатке или несколько вводов за день мгновенно
   пересчитываются): `perDayPlan = (income − Σ бюджетов фикс. категорий −
   buffer) / длина цикла`, опережение = `(perDayActual − perDayPlan) × daysLeft`
   — в деньгах «сколько можно потратить сверх плана до зарплаты». Доход —
   синхронизируемый скаляр `monthlyIncome` (+`meta.monthlyIncome`, 0 = «не
   задан», индикатор скрыт), редактируется в **Settings → Budget**
   (`SettingsTab/BufferCard`). Математика — `computePace` /
   `computeCycleLength` / `plannedObligatoryTotal` (`src/lib/math.ts`); UI —
   pill в строке лейбла виджета (`DashboardTab/PacePill`: зелёный — опережение,
   красный — отставание, нейтральный «on plan» при |ahead| < 1; токен
   `--green-tint`) + строка «Pace vs plan» в «Show breakdown». План **следует
   цели выбранной вкладки** (ветка `daily-widget-improvement`) — целевому
   свободному остатку к зарплате: savings+buffer (Grow), savings (Keep), 0 —
   копилка тратится равномерно (Spend; та же метрика у deficit-карточки).
   Параметр `buffer` в `computePace` ≡ `target − savingsPool`, поэтому три цели
   = `buffer` / `0` / `−savingsPool`; соседние варианты расходятся на
   `(buffer|pool) × daysPassed / cycle`. Справа от pill — кнопка (i): модалка
   `DashboardTab/PaceInfoModal` показывает расчёт на данных пользователя
   (план: доход − фикс. по плану − цель ÷ длина цикла; факт: баланс − остаток
   фикс. − цель ÷ дней осталось; (факт − план) × дней = pill). Разбор — чистая
   `explainPace` (`math.ts`), гарантированно совпадает с pill. Тесты —
   `test/lib/pace.test.ts`, `test/lib/paceExplain.test.ts`,
   `test/storage/monthlyIncome.test.ts`.
3. **Один виджет по ситуации** — ✅ **реализовано** (ветка
   `daily-limit-improvements`). Три карточки заменены одним адаптивным виджетом;
   `computeSituation` (`src/lib/math.ts`) выбирает состояние и дневную цифру,
   `DashboardTab` красит виджет, три дневных числа уехали в «Show breakdown».
   Тона/токены `teal`/`orange`. Тесты — `test/lib/situation.test.ts`. Состояния:
   - приятный зелёно-синеватый (teal) — опережает буфер (держит всю подушку);
   - зелёный — не залезает в копилку;
   - оранжевый — залезает в копилку;
   - красный — превышает все траты, включая копилку.

   Два инварианта корректности (аудит формул, ветка `daily-widget-improvement`):
   - **день зарплаты 29–31 в коротком месяце** — «зарплата уже пришла?»
     сравнивается с клампнутым днём (`effectiveIncomeDay` в `math.ts`), иначе
     последний день короткого месяца давал `daysLeft = 1` вместо полного нового

     Леджер (финализация, таблица) остаётся знаковым. Тесты —

## Счета
**Статус: реализовано** (ветка `currency-and-accounts`). Единый баланс
(`bank`/`bankExpr`/`bankCurrency` + `meta.bank`) заменён коллекцией
`accounts: Account[]` (`id`, `name`, `balance`, `balanceExpr?`, `currency`,
`updatedAt`/`deletedAt`). Баланс для прогноза = **сумма живых счетов, каждый
пересчитан в валюту отображения** (`accountsTotal` в `convert.ts` →
`projectToDisplay().bank`); `math.ts` не менялся.

- **UI** — `DashboardTab/BalanceCard`: свёрнуто — итог в валюте отображения без
  селектора + шеврон; тап раскрывает список: подпись (имя или код валюты), поле
  остатка с формулами (в валюту счёта), `CurrencySelect` box, меню `…`
  (Rename — инлайн, Move up / Move down, Delete — тост с Undo; неприменимые
  пункты скрыты: у первого нет Move up, у последнего — Move down, у
  единственного — Delete), кнопка
  «+ Add account» (счёт в валюте отображения, фокус в его поле). Ввод — всегда
  через список; пустая установка (все остатки 0) показывает список раскрытым.
  Раскрыт/свёрнут — локальный `uiPrefsStore.accountsOpen` (не синкается). Одна
  общая строка свежести (`balancesUpdatedAt`).
- **Порядок** — поле сущности `order` (`lib/accountOrder.ts`), не позиция в
  массиве: merge держит локальный порядок массива, а `docKey` сортирует по id,
  так что перестановка по позиции не синкалась бы. `order` дробный — перемещение
  переписывает **только сдвинутый счёт** (середина между новыми соседями),
  чтобы не перебить чужую несинкнутую правку соседних счетов. Счета без `order`
  (созданные до этого) ранжируются по индексу; первое перемещение разово
  перенумеровывает живые счета 0…n-1 (так же при равных `order` после merge или
  исчерпании точности). Новый счёт — в конец (`nextAccountOrder`).
- **Минимум один счёт**: `deleteAccount` отказывает (false) для последнего
  живого. Если два устройства удалили разные счета, после merge живых может не
  остаться — тогда итог 0 и кнопка «Add account»; счёт автоматически не
  создаётся (иначе каждое устройство создало бы свой).
- **Миграция** (`migrateAccounts` в `persist.ts`): документ без `accounts` →
  один счёт с **детерминированным id `main`** (`MAIN_ACCOUNT_ID`) из старых
  `bank`/`bankExpr`/`bankCurrency`, `updatedAt` = старый `meta.bank`. Два
  устройства, мигрирующие независимо, дают одинаковую сущность → merge без
  удвоения баланса. Документ с массивом `accounts` берётся как есть (даже
  пустой). `coerceBudgetState` принимает `accounts` или legacy `bank`.
- **Merge** — `accounts` сливаются по сущности как категории (LWW по
  `updatedAt`, tombstone, conflict-copy `kind: 'account'`); остаток, формула и
  валюта всегда с одной стороны.
- **Совместимость**: новый документ **без `bank`** → клиент до этой версии его
  не примет (ошибка синка) вместо того, чтобы переписать без счетов. Legacy-файл
  остаётся legacy, пока новому клиенту нечего добавить (без эха); первая
  реальная правка пишет форму со счетами.

Тесты — `test/storage/accounts.test.ts` (миграция, санитайз, действия, правило
«минимум один», merge, свежесть), `test/lib/accountOrder.test.ts` (порядок,
перемещения, перенумерация, синк), `test/lib/convert.test.ts` (сумма счетов,
превью), `test/lib/dashboard.test.ts`, `test/e2e/accounts.e2e.test.ts`
(через настоящий sync-движок); харнесс `syncHarness` маппит legacy `bank` на
счёт `main`.

## Финализация месяца
**Статус: реализовано** (ветка `adjustments`). Финализация фиксирует прирост
копилки за месяц **без вычета фикс-расходов**: `saved = current balance −
prior savings pool` (`computeFinalize(bank, savings)` в `src/lib/math.ts`).
Прежняя формула вычитала ещё `obligatoryTotal` (остаток неоплаченных фикс-
расходов) — это занижало результат на сумму ещё-не-оплаченных счетов, хотя по
факту деньги на счету. Почему так правильнее:
- накопленный итог колонки «Balance at end» теперь равен **реальному балансу в
  банке** на момент финализации (раньше — `bank − oblig`);
- «Saved this month» читается как честная помесячная дельта: поскольку
  `prior pool = bank на прошлой финализации`, получаем `saved = доход − все
  траты цикла` (что не отложил из этой зарплаты);
- в типичном случае (финализируешь в конце цикла, счета оплачены, `oblig ≈ 0`)
  старая и новая формулы совпадают — расхождение лишь при неоплаченных счетах,
  где новая честнее и self-correcting (в духе минимальной модели).
- Следствие для дашборда: savings pool теперь = весь карри-овер баланс, т.е.
  дневной бюджет тратит только прирост с прошлой зарплаты (это и есть смысл
  «бюджет до следующей зарплаты»). В обычном кейсе (`oblig ≈ 0`) поведение не
  меняется.

**Повторная финализация месяца** (строка за текущий месяц уже есть): строка,
которую финализация перезапишет (`finalizeTargetIndex` — первая живая строка
месяца), **не входит** в prior pool (`computeFinalize(bank, savings, month)`).
Раньше она считалась, и итог после перезаписи расходился с балансом (3500 при
строках 1000 + 500 → записывалось 2000 вместо 2500). Теперь финализация
идемпотентна, а дубликаты месяца (кроме перезаписываемого) остаются в пуле.
Тесты — `test/lib/finalize.test.ts`.

Тоггл **«Reset spent for fixed expenses»** в модалке финализации — теперь
**синхронизируемый скаляр** `resetSpentOnFinalize` (+`meta.resetSpentOnFinalize`,
default `true`), а не разовый per-finalize чекбокс. Мёржится по времени как
`buffer`/`currency`/`monthlyIncome` (`mergeScalars`), `coerceResetSpentOnFinalize`
чтит только явный boolean (иначе default `true`), чекбокс в `SavingsTab` привязан
прямо к стору через `setResetSpentOnFinalize`. Привычка обнулять `spent` следует
за пользователем между устройствами. Тесты —
`test/lib/finalize.test.ts`, `test/storage/resetSpentOnFinalize.test.ts`.

Поскольку месяц теперь может быть **отрицательным** (потратил больше, чем
заработал), поле «Saved this month» в таблице копилки перешло с `type="number"`
на локально-черновой `SavedInput` (`src/components/SavingsTab/SavingsTable.tsx`):
контролируемый `type="number"` не держит ведущий `−` (браузер отдаёт пустую
строку), поэтому компонент хранит строковый draft при редактировании и коммитит
распарсенное в стор; полная клавиатура на мобильном (у decimal-клавиатуры нет
минуса — тот же компромисс, что у `MathField`, см. a11y ниже).

## Dropbox-синхронизация — переработка надёжности
**Статус: реализовано** (ветка `storage-improvements`). Все три слоя ниже
собраны: CAS через `rev`, слияние по сущностям с tombstone, conflict-copy.
Чистая логика слияния — `src/sync/merge.ts`; движок (rev-трекинг, CAS-retry,
conflict-copy, `push()`) — `src/sync/dropbox.ts`; per-entity `updatedAt`/
`deletedAt` и `meta` для скаляров — в `src/types.ts`/`budgetStore.ts`. Покрыто
e2e: `test/e2e/dropboxSync.e2e.test.ts` (фейковый Dropbox с rev-семантикой).
Раздел ниже сохранён как исходный замысел.

Прежняя схема была опасна: «самый свежий целый файл
побеждает». Единица конфликта — весь `budget.json`, победитель по `updatedAt`
(часы клиента), запись `mode: 'overwrite'` без проверки `rev`, pull только при
загрузке. Реальные сбои: (1) тихая потеря несвязанных правок с двух устройств —
затирается весь документ, включая неконфликтующую правку; (2) lost update между
pull и push; (3) побеждает не «кто новее», а у кого часы спешат.

Решение — сменить принцип на «сравни-и-запиши + слияние по сущностям». Данные
ложатся на merge: независимые сущности `bank`, `incomeDay` и две коллекции с
ключами (категории по `id`, сбережения по месяцу). Три слоя:

1. **Compare-and-swap через Dropbox `rev`** (обязательно, дёшево) — писать
   `mode: { update: <последний известный rev> }` вместо `overwrite`. При
   изменившемся файле Dropbox сам вернёт конфликт вместо тихого затирания.
   Убивает сбой №2.
2. **Слияние по сущностям** (главная ценность) — при конфликте брать новейшую
   версию КАЖДОЙ сущности отдельно, а не весь свежий файл. Требует per-entity
   `updatedAt` + **tombstone на удаление** (иначе merge воскресит удалённую
   сущность из устаревшей копии). Превращает сбой №1 из потери данных в чистое
   слияние. Полноценный CRDT избыточен.
3. **Conflict-copy как страховка** (дёшево) — если две правки одной сущности
   реально столкнулись и автослияние не уверено, сохранять проигравшую версию
   рядом (`budget (conflict <устройство> <время>).json`), не выбрасывать.

Рекомендация: минимум — слои 1 + 3 (убирают тихую потерю данных). Правильно —
добавить слой 2 (закрывает реальный сценарий «правил на телефоне и на ноуте —
ничего не потерялось»). После CAS+merge перекос часов перестаёт быть
катастрофой; при желании добить — счётчик версий на устройство вместо wall-clock
(тонкая шлифовка, не приоритет).

## Запланированные улучшения (план)

### Надёжность хранения (localStorage)
**Статус: реализовано** (ветка `storage-improvements`). Логика — чистые модули
`src/lib/storagePersistence.ts` (обёртка persist/persisted/estimate +
`initStoragePersistence`, запрос при первом осмысленном вводе, не cold-on-load) и
`src/lib/backupNudge.ts` (`hasMeaningfulData`, `shouldShowBackupNudge`). UI:
постоянный чип-индикатор «Protect your data» в хедере (`Header/BackupNudge`) с
модалкой-объяснением и Connect Dropbox; статус хранилища — `SettingsTab/
StorageCard`. Покрыто unit-тестами `test/storage/*`. Замысел ниже.

НЕ мигрировать на IndexedDB ради надёжности — это тот же класс «script-writable
storage», Safari ITP вычищает его так же (7 дней без открытия), выгоды ноль.
Решение из двух дешёвых слоёв, прозрачно для текущей архитектуры (Zustand
продолжает писать в localStorage):
1. **`navigator.storage.persist()`** при первом осмысленном вводе — помечает
   хранилище persistent, браузер перестаёт вычищать под нехватку места и по
   ITP-таймеру. В Settings статус через `navigator.storage.persisted()`.
2. **Копия вне устройства** — единственное, что переживёт очистку данных/смену
   телефона. Уже есть Dropbox-синк и экспорт JSON; добавлен мягкий разовый намёк
   подключить синк / скачать бэкап тем, кто синк не подключил.

### Замена нативных диалогов
**Статус: реализовано** (ветка `claude/remaining-features-zzi7ou`). Все
`confirm()`/`alert()` убраны. Подтверждения (Finalize month с превью формулы,

### Валюта у сумм / валюта отображения
**Статус: реализовано** (ветка `currency-and-accounts`). Раньше суммы были
безвалютными (неявно в `state.currency`), и смена EUR→AMD лишь меняла подпись
(€1500 → ֏1500) без возможности пересчёта. Теперь **каждая сумма хранит свою
валюту**, а `state.currency` (имя оставлено ради совместимости синка) — только
**валюта отображения**: итоги и прогноз пересчитываются в неё на лету по
сегодняшнему кэшированному курсу (плавающий курс ожидаем; старая копилка — тоже
по сегодняшнему). Смена валюты отображения меняет одно поле — данные не трогаются,
EUR→AMD→EUR возвращает исходные цифры.

- **Теги**: `bufferCurrency` / `monthlyIncomeCurrency` — без своих `meta`,
  едут под меткой своей суммы; `Account.currency`, `Category.currency` (одна на
  budget+spent) и `SavingsRow.currency` — часть контента сущности (с ветки
  `currency-and-accounts` единый `bank`/`bankCurrency` заменён счетами — см.
  «Счета»). Merge берёт тег с победителя суммы — число одного
  устройства не склеивается с валютой другого.
- **Миграция**: `normalizeBudgetState` заполняет отсутствующий тег **валютой
  самого документа** (`coerceCurrencyTag`) — в старых данных всё неявно в ней.
  Работает для импорта, remote pull, `replaceState` и rehydrate (persist
  `merge` прогоняет сохранённое через нормализацию; shallow merge дал бы
  дефолтный EUR). Чистая миграция формы: метки не бампаются.
- **Конвертация** — `src/lib/convert.ts` (чистый, без стора): `makeRateResolver`
  (перенесён из `rates.ts`, там re-export), `convert`, `makeConverter` (нет
  курса → 1:1 + `missing`, дашборд показывает предупреждение),
  `projectToDisplay`, `computeFinalizeIn`, `thresholdScale`. `math.ts` остаётся
  безвалютным; тело дашборда вынесено в чистую `computeDashboard`. Хуки —
  `lib/useDisplayBudget.ts`.
- **Правила**: новые суммы получают валюту отображения; валюта сущности
  меняется только явно (`CurrencySelect` в модалке категории, у счёта, у
  буфера/дохода) и это **переподпись**, не пересчёт — формула переоценивается в
  новую валюту (`setAccountCurrency`). Формулы считаются в валюту своей сущности
  (`useRateResolver(target)`), поэтому снимок `bank`/`budget` всегда в ней.
  Строки категорий — в своей валюте (символ, если ≠ отображения), итоги — в
  валюте отображения.
- **Подтверждение смены** — выбор в пикере Settings → Budget не переключает
  сразу, а открывает `SettingsTab/CurrencySwitchModal`: короткое объяснение
  («итоги и дневной бюджет — в новой валюте, введённые данные не меняются») +
  наглядные строки на данных пользователя «было → станет»
  (баланс в своей валюте, остаток фикс-расходов, копилка; без данных — круглый
  пример ≈100 €). Без курса строки

  `refreshRates`. Переключение — только по кнопке. Логика — чистая
  `previewCurrencySwitch` (`convert.ts`).
- **Финализация** — в валюте отображения (баланс теперь — сумма счетов в

### Валюта в формулах
**Статус: реализовано** (ветка `currency-in-formulas`). В любом amount-поле с
формулой (`MathField` = Budget/Spent в модалке категории + Current balance) можно
писать сумму в другой валюте — `10 AMD`, `$10`, `10 ₽` — и она конвертируется в
дефолтную валюту в момент вычисления. Слои:

- **Парсер** (`src/lib/evalExpr.ts`): `evaluateExpr/evaluateLenient` получили
  опцию `rate?: (token) => number | null` (мультипликатор `токен → дефолтная
  валюта`). Валютный токен (суффиксный ISO-код `[A-Za-z]+`, префиксный/суффиксный
  символ) распознаётся **только при переданном resolver** — без него поведение
  1-в-1 старое (обратная совместимость, старые тесты не трогаются). Токен связан
  на уровне atom, т.е. крепче `*`/`+` (`2 * 3 USD` = `2*(3 USD)`). Неизвестный код
  → resolver `null` → формула невалидна (не «тихий ноль»). Добавлен
  `hasCurrencyToken`.
- **Курсы** (`src/lib/rates.ts`): бесплатный **keyless** fawazahmed0 currency-api
  (jsdelivr CDN + fallback `.pages.dev`, ~339 валют, обновление ~раз в день).
  Таблица `values` = «1 base = N единиц X», поэтому **кросс-курс между любой
  парой выводится через base** — `makeRateResolver` конвертирует даже когда
  `base ≠ дефолтная валюта` (текущая валюта резолвится в 1 всегда, даже без
  курсов — это identity). `fetchRates`/`parseProviderResponse` (чистые),
  `refreshRates`/`ensureRatesFresh` (IO), `useRateResolver` (хук, реактивен к
  `rates`+`currency`).
- **Хранение**: курсы — синхронизируемый скаляр `rates: ExchangeRates | null`
  (+`meta.rates`), мёржится LWW как `buffer`/`currency` (`mergeScalars`,
  `coerceRates` в `persist.ts` санитизирует недоверенное). Кэш переживает
  перезагрузку, работает офлайн, и фетч одного устройства достаётся остальным.
- **UI**: `SettingsTab/RatesCard` — дата последнего обновления
  (`formatUpdatedAgo(meta.rates)`), статус-точка, кнопка **Refresh now**.
  Авто-рефреш раз в день из `App` (`ensureRatesFresh`, триггеры: нет кэша /
  возраст ≥1 дня / `base ≠ currency`).

Решения: (1) набор валют для формул = вся таблица курсов (200+), шире, чем
`CURRENCY_CODES` (пикер отображения). (2) Символы — кураторская карта
`SYMBOL_TO_CODE` (`currency.ts`), однозначные; `$`→USD, `¥`→JPY (компромисс);
основной путь — ISO-код. (3) **Персистентность как формула**: запись с валютой
(как и с арифметикой) сохраняется в `balanceExpr`/`budgetExpr` и переоценивается
живьём — иначе `useEffect` в `BankInput` затирал бы `10 AMD` конвертированным
числом при фокусе; дрейф за сутки крошечный и self-correcting, а числовой
снапшот (`bank`/`budget`) всё равно хранится и питает дашборд. (4) «Нет курса» →
кэш, иначе формула невалидна. Тесты — `test/lib/evalExpr.test.ts`,
`test/lib/rates.test.ts`, `test/storage/rates.test.ts`,
`test/e2e/ratesSync.e2e.test.ts`.
